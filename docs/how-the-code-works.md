# How the code works

A guide for developers. For using the app, see the [README](../README.md).

## The big picture

This repository has two tools, each a single web page with no server of its own: the Map Generation Tool, described here, and Unofficial, which works the same way for unofficial coverage (its differences are listed after this list; how they share code is in "Two tools, one code"). The Map Generation Tool is a single web page with no server of its own. Everything happens in the visitor's browser. It builds [map-making.app](https://map-making.app) maps of random official Google Street View locations that match what the visitor chooses. What comes next is in [the plan](plan.md).

1. **Settings.** The visitor picks where (one or more countries, a continent or the whole world), what each location must have (no road name, not on a major road, the end of the coverage, an intersection or no arrows at all, photos from a certain period (month and year), in any mix) and how many locations.
2. **Locations per country.** With more than one country, the number is split between them in the proportions of a well-known GeoGuessr map, from [Vali](https://github.com/slashP/Vali) by slashP, in whole numbers that add up (largest remainder method). The table under the steps shows the split before the search and the progress during it.
3. **Random spots.** The page keeps choosing a country that still needs locations, and a random spot inside it, using the country borders of the built-in country-coder library, spread evenly by area. The borders reach far out to sea (New Zealand's shape is about 87% sea), so only spots on land are kept, from a land map built into the page (`src/land.js`, made from Natural Earth's land outlines in the world-atlas package: a grid of cells about 5 km wide, where a cell with any land in it counts as land, so small islands and coasts are kept).
4. **Google.** For each spot, Google's Maps JavaScript API is asked for the nearest official outdoor panorama within the chosen radius. This leaves out some indoor panoramas, but not all of Google's own: Google counts some of them as outdoor coverage, and nothing in its answer tells them apart (see "Known limits" in the plan). Its answer includes the panorama's arrows: their labels are the road names, a panorama with one arrow is where the coverage ends, one with three or more is an intersection, and one with none is a photo on its own ("No arrows at all").
5. **Cameras.** The image size that comes with Google's answer tells the camera (`cameraOf`): 8192 pixels high is Gen 4; 6656 is Gen 2/3, or bad camera when the photos are from 2020 on, as in Vali, except in India, Nepal, Nigeria, Lebanon, and São Tomé and Príncipe; 1664 (3328 × 1664, 2007–2008) is Gen 1, which is left out of every search; other sizes (Sydney has 12000 × 6000 photos from 2017–2018) count as an unknown camera, kept unless cameras are chosen. The sizes were checked on real panoramas in San Francisco and Sydney with the owner (October 2026). The visitor can choose cameras (Gen 4, Gen 2/3, bad camera), or, without a choice, leave out only bad camera ("No bad camera"). If "Use an older photo instead" is ticked (it is off by default) and the newest photo at a spot is not a camera asked for, the newest older photo there that is is used instead; it comes from the list of photos Google's answers carry (`time`, which Google does not document), and is checked like any other panorama.
6. **Keep or skip.** A panorama that matches, lies in that country and is at least 100 m from every location so far becomes a location. Several lookups run at once until every country has its number or the visitor stops. While it runs, the status line forecasts the time left ("time left" in `src/app.js`): for each country, the random spots it can be expected to take until it is full or gives up (where locations are rare, giving up is likely), from the spots one location has cost there so far; added up and divided by the spots per second.
7. **Shortfalls.** A country gives up after a set number of random spots in a row without a new location (2,000 by default; failed lookups do not count), unless giving up is switched off ("Give up on a country after" unticked, `giveUpOn`): then no country gives up and the search runs until it is full or stopped, and the time left reads "unknown" while such a country has found nothing yet. If countries fell short, the page offers to share the missing locations between the countries that finished, in their proportions, and search on, or to keep what was found.
8. **Export.** The locations download as a map-making.app JSON file, each with its country code and the tags the visitor ticked: the country's name (ticked by default), "No road name", "Dead end", "Intersection" and "No arrows" (each a separate option) where they apply, and the date of the photos, as the year (2023) or month and year (04-2023), and the camera (Gen 4, Gen 2/3, Bad camera). The map shows only the first `MAX_DRAWN` locations (20,000): every dot is redrawn when the map moves, and more would make zooming and panning slow (measured October 2026: 50,000 dots make each zoom wait half a second to a second). The welcome dialog tells visitors.
9. **Map file size.** The download button shows the file's exact size (`fileBytes`; 1 MB is 1,000,000 bytes, the stricter reading). Over the size limit ("Keep the map file under", 20 MB by default, as some places such as Discord take no larger uploads), the page offers to make it smaller once the search has stopped. Each country keeps its share of a smaller total (`splitTotal`); within each country, either the locations closest to others are dropped, for an even spread (`spreadPick`: the largest spacing that still leaves enough locations, found by halving the range of spacings, with a grid of cells in space to find near locations fast), or random ones. The total starts from the average size of a location and is lowered until the file fits. The smaller set replaces the results (the map and counts follow), and "Undo" brings the full set back until the next search or "Clear". About 4 seconds for 130,000 locations with an even spread (measured October 2026).
10. **Resuming.** While a search runs, it is saved in the browser's IndexedDB (settings, locations, each country's progress; never the key). On the next visit, a box offers to continue it, download what was found, or discard it. A finished search is not kept. Within a visit, a search stopped by hand can be continued with "Continue the search" while the settings that decide which locations are found are unchanged (`fitKey`: all settings but the map file's name, tags and size limit, and `RUN_SETTINGS`: the number, the radius, the lookups at the same time and giving up). Those may change, also after a search that ended: a higher number looks for more, a lower one keeps that many at random, each country its share (`continuePlan`). With other settings, "Start a new search" is the only choice: a warning says it starts from scratch, and for a stopped search a dialog asks first and names the sections that changed (`confirmNewSearch`, `changedSections`).

**Unofficial** differs in these steps: every country and territory is offered, Antarctica too (`COUNTRY_FACTS`, made by `src/countries.js`); the locations are shared by land area, population, population density (people per km² of land) or in equal shares (`builtInShare`; the populations come from Natural Earth, in `src/data/population.json`); Google is asked for the nearest panorama of any kind (source "default": "outdoor" would leave out every photosphere, as Google cannot tell whether one is indoors), and only those that are not Google's own are kept (`isOfficial`), so Google's own coverage nearby hides unofficial coverage and is counted as "official coverage instead"; its filters are the period, whole 360° photos (an image twice as wide as high), the image height, with or without arrows, and the uploaders (from the copyright, "© 2023 Jane Doe"); there are no cameras or older photos; the tags are the country, the uploader, "Arrows" or "No arrows" (every location gets one of the two) and the date; a country gives up after 5,000 spots by default (`GIVE_UP_DEFAULT`, each tool's own); and there is no "Camera view": the camera faces the middle of the photo (`centerHeading`), level, at zoom 0.

Much of the code is copied from [Lookout (osm-tool)](https://github.com/ugerhard-git/osm-tool). The two apps keep separate copies on purpose. When a feature needs a part Lookout already has (Overpass queries, the official-coverage check, street names, shareable links, history of searches), copy it from Lookout's `src/app.js` and adapt it.

## Two tools, one code

This repository has two tools: the **Map Generation Tool** (official coverage, at the site's main address, from `src/page.html`, `src/style.css` and `src/app.js`) and **Unofficial** (unofficial coverage, at `unofficial/`, from the same files in `src/unofficial/`). See the plan, "A second tool: Unofficial".

Most of the code is the same for both and lives once, in `src/shared/`. Each tool's `app.js` holds only what is its own, and a line `/*SHARED <file>*/` wherever a shared file goes; the build puts them together (`src/assemble.js`), so each page is still one file and reads as one script. The order matters only for code that runs while the page loads: a tool's part comes before the shared file that uses it then.

## A third tool: Distribution

`src/distribution/` is a page of a different kind: one map file in, a table of countries, territories or continents out, with a CSV and an Excel download. It has no map, no Google key and no outside connections, so the build gives it no Leaflet, land map or Google (`buildPage` with `map: false`), and its security policy allows no outside host at all (`connect-src 'none'`). It puts in only `src/shared/style.css`: the shared code is about searches. Its `app.js` explains how it works at the top; in short:

- **Which country** (`placeOf`): the file's `countryCode` first; the position (country-coder, territory level) where it is missing, and to make a country's code exact where a location lies in one of its territories.
- **Views** (`viewRows`): every place on its own; territories counted with their country (`PLACES[code].country`) except `KEEP_SEPARATE`; continents (`PLACES[code].continent`, from `distributionFacts` in `src/countries.js`).
- **Downloads:** `csvText` (the view shown, in the number format chosen: `point` or `comma`, detected from the browser for `auto`) and `xlsxFile`, which writes an Excel workbook itself (XML files in a zip archive stored without compression, `zipFiles`), with the tabs from `workbookSheets`.

Tests: `tests/distribution.js`.

## Rules worth knowing before you change something

- **Edit `src/`, never `dist/`.** Run `npm run build && npm test` after every change.
- **No inline event handlers.** The page's security policy only runs the scripts the build fingerprinted, so `onclick="…"` in the HTML does nothing. Wire events up in `app.js`.
- **No new outside scripts or CDNs.** Libraries are installed with npm and embedded by the build.
- **The page may only connect to Google's Maps service** (`maps.googleapis.com`). A feature that needs another service adds just that host to `connect-src` in `src/build.js`, and `tests/security.js` with it.
- **Treat everything from outside as untrusted:** Google, uploaded files and saved settings. Check values before use, and put text on the page with `textContent` or through `esc()`.
- **Never put keys in the code, in shared links or in error messages.** The site key comes from the `GOOGLE_API_KEY` environment variable at build time.
- **Interface text is for non-technical people:** plain words, sentence case, say what happened and what to do.

## Formatting

The code is formatted with [Prettier](https://prettier.io). `npm run format` formats everything, and `npm run format:check` checks it, which also runs on every pull request. With the recommended VS Code extension, files are formatted when you save.

## Linting

[ESLint](https://eslint.org) looks for likely mistakes: names that do not exist, variables that are never used, code that has no effect. `npm run lint` runs it; it also runs on every pull request, and the recommended VS Code extension underlines problems as you type. The settings are in `eslint.config.mjs`. They lint each tool's `app.js` with the shared code put in, as the page gets it, so names one part defines and another uses are known and unused ones are still found; a problem in shared code is reported on its `/*SHARED …*/` line, naming the shared file and line. They know which names the pages provide besides `app.js` (Leaflet's `L`, the Vali data `VALI`, Unofficial's `COUNTRY_FACTS`, `FRAMED`, `google`), and they let the tests use both tools' top-level names inside `page.evaluate`, read straight from the code.

## Tests

```sh
npm run build
npm test              # all test files
npm test -- search    # only files whose name starts with "search"
```

Each test file prints `PASS …` or `FAIL …` lines and ends with `ALL PASS`. Screenshots of some states are saved in `dist/screens/`. To test something new, copy the setup of a test file close to your feature: `tests/search.js` shows how to decide what the simulated Google answers.

When writing a test:

- **Open the page with `openPage`** from `tests/helpers.js`. It loads the page from `PAGE` (or Unofficial from `UNOFFICIAL`, `tests/site.js`) rather than from disk, simulates Google's script and the map tiles, and shortens waits, so the tests run offline, fast and need no key. Set `window.__sv` in the page to decide Google's answer to each request.
- **Start Playwright from `tests/pw.js`**, which dismisses the first-visit welcome dialog, unless the test is about that dialog.
- **End with `ALL PASS`** when every check held; `tests/run.js` looks for it.
- **`tests/valitool.js` needs no browser:** it runs `tools/vali.js` on made-up copies of Vali's files in a temporary folder. **`tests/populationtool.js`** does the same for `tools/population.js`, with made-up tables.
- **`tests/assemble.js` needs no browser either:** it checks how `src/assemble.js` puts the shared code into a page.
- **Shared code is tested through the Map Generation Tool's tests.** `tests/unofficial.js` tests what is Unofficial's own.

## Publishing

Every push to `main` builds the pages with the site key (the `GOOGLE_API_KEY` secret, handed only to that build step) and publishes them to GitHub Pages (`.github/workflows/deploy.yml`): the Map Generation Tool at the site's main address, Unofficial at `unofficial/`, Distribution at `distribution/` (it has no key). The tests run first, on a build without the key.

## Updates

Dependabot (settings in `.github/dependabot.yml`) proposes updates once a month, as pull requests:

- **Development tools** (Playwright, Prettier, ESLint): their minor and patch updates come together in one pull request. A major update comes on its own, as it may need changes here.
- **Leaflet, country-coder, the font and world-atlas (the land map):** one pull request each. These end up in the published page, so check the page itself after merging.
- **GitHub Actions:** together in one pull request.

Only versions that have been out for at least a week are proposed. Security fixes are proposed straight away.

**Vali's data** is not a package, so Dependabot cannot watch it. `.github/workflows/vali.yml` does instead, on the 3rd of every month (and when started by hand under Actions → Update Vali data → Run workflow):

1. The job "check" clones the latest Vali and runs `tools/vali.js`. If the distributions and continents are the same as in `src/data/vali.json`, it stops there.
2. If they changed, the same job runs the formatting check, lint, build and all tests. It has no write access: it installs and runs the npm packages, and a package that turned bad could otherwise misuse the token.
3. The job "propose" imports the same Vali commit again, with only `tools/vali.js` (no packages installed), checks that nothing but `src/data/vali.json` changed, pushes it to the branch `vali-update` and opens a pull request (or updates the open one) that lists what changed: maps added or removed, countries added or removed, the largest changes in shares, and any slips found in Vali's data. Only this job can push, and only its last step gets the token for `gh`. Keep it that way: no `npm ci` or tests in "propose".
4. Pull requests opened by a workflow do not start the Tests workflow, so "propose" starts that workflow on the branch itself; the required "test" check then runs as usual.

If Vali's files look wrong, the import stops, the run fails and GitHub notifies the owner. For this to work, the repository setting "Allow GitHub Actions to create and approve pull requests" must be on. A new map in Vali gets a name made from its list name; add a proper name to `MAP_NAMES` in `tools/vali.js`.

**Natural Earth's populations** (Unofficial) change rarely, so they are updated by hand, not by a workflow. Download `10m_cultural/ne_10m_admin_0_map_units.dbf` of the latest commit of [natural-earth-vector](https://github.com/nvkelso/natural-earth-vector) (the address is in the comment at the top of `tools/population.js`), run `node tools/population.js <file> --commit <commit>`, look at what it says it left out, and open a pull request with the new `src/data/population.json`. The file in use is from commit `ca96624` (June 2022).
